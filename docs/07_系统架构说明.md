# 系统架构说明

## 总体架构

AI课程顾问 Agent 使用 Next.js App Router 构建全栈应用。`src/app/page.tsx` 输出页面入口和运行环境开关，`src/components/CourseAdvisor.tsx` 负责 React 交互界面、消息列表、结构化推荐卡、快捷动作、重试、移动端滚动和 Markdown 导出。前端代码使用 TypeScript 和 CSS Modules，不包含模型密钥、数据库连接串或课程规则的可信来源。浏览器只能访问公开页面和项目提供的 Route Handler，不能直接访问大模型服务或 Supabase 数据库。

服务端接口集中在 Route Handler。`POST /api/chat` 接收用户消息、会话状态、动作、`sessionId` 和稳定请求 ID，调用会话编排、检索、规则、模型和校验链路后返回公开响应。`POST /api/history/sessions` 创建服务端会话，`GET /api/history/sessions/[sessionId]/messages` 恢复历史消息。服务端在请求运行时读取必要环境变量，构建阶段和浏览器端不读取 Secret Key。

## 会话存储

会话持久化通过 `ConversationStore` 统一接口收口，接口包含创建会话、追加消息和查询消息。上层 API 不判断具体存储类型；`createConversationStore()` 按服务端环境变量选择 Supabase、本地 JSON 或 Blob 实现。Production 使用 Supabase PostgreSQL，核心表为 `chat_sessions` 和 `chat_messages`。两张表启用 RLS，浏览器没有匿名直连策略，服务端使用 `SUPABASE_SECRET_KEY` 或兼容后备 `SUPABASE_SERVICE_ROLE_KEY` 执行受控读写。浏览器本地只保存不透明 `sessionId`，刷新时用历史接口恢复消息、UI 元数据和最新会话状态，不保存消息数组、模型配置或数据库凭据。

## 知识检索与生成

运行时知识库包含 83 个知识块，覆盖学生资料、教师资料和机构及学校资料。每一轮回答前，检索器结合用户身份、当前实体、已采集约束、待追问键、当前消息和最近历史，选择 5 至 8 个相关知识块。当前班型或机构服务优先参与检索，完整目录后的短追问会收拢到用户明确选择的实体；资料外问题不会注入无关块凑数。

被选中的知识块以转述资料、稳定 ID 和必要结构字段注入大模型。模型采用严格 JSON 生成，只能返回面向用户的 `answer`、本轮使用的 `usedChunkIds` 和追问建议。程序随后校验 JSON 结构、`usedChunkIds` 合法性、金额、日期、实体和必要事实。`usedChunkIds` 必须来自本轮 `retrievedChunkIds`，不能引用未注入知识块；知识型回答至少使用一个有效块。通过校验后，程序根据合法块追加资料来源，来源章节不由模型自由生成。

## 规则层与职责分工

推荐规则、费用、日期、边界和来源由 TypeScript 确定性代码负责。学生推荐读取营期、城市、线上线下、回放、出行和食宿；教师推荐读取等级、前置条件和时间形式；机构及学校咨询只进入素材 C 资料域。费用复算在规则层完成，早鸟和团报按优惠额择优，食宿只对线下学生班生效，学校采购 20 人回答 5 万元起且不混入个人课程价格。

大模型负责在已确认事实内组织自然语言正文和理由，不负责决定金额、日期、实体、优惠、来源章节或服务范围。程序会拦截未授权金额、未提供事实、外部承诺、来源伪造、跨身份串线和资料外扩写。模型 5xx、超时、非法 JSON 或 grounding 失败时最多静默重试一次；仍失败则返回脱敏、可重试的公开错误。

## 发布与验证

Preview 和 Production 通过 Vercel Git Integration 生成。功能分支推送后等待新的 Preview Deployment 达到 READY，再验证首页和主要 JavaScript 资源 HTTP 200、会话创建、用户和 AI 消息保存、刷新恢复、学生 9 个班型、教师 6 个班型、当前班型组合追问、第五天课程 RAG、会员价格边界、学校采购边界、Markdown 导出、普通页面无内部诊断、Production 模式构建隐藏 Viewport Debug，以及无 HTTP 500 或可见 grounding 错误。

Preview 全部通过后，以非快进方式合并 `feature/b-level-v2` 到 `main`，重新运行 Vitest、TypeScript、ESLint、Production Build 和 `git diff --check`，再推送 `main`。Production 自动部署 READY 后，核对 Target、Git SHA、七项 Production 变量名称、正式域名指向和构建日志，再执行正式冒烟。若新 Production READY 后冒烟失败，应停止后续测试，将发布前记录的旧 Production Deployment 重新 Promote 为 Production，并通过正常 Git revert 处理代码撤销，不使用 reset、rebase 或强制推送。
